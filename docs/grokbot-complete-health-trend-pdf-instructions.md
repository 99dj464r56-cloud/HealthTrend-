# Grokbot 完整执行档案：Health Trend PDF

这份文件汇总 Astra 的只读评审建议、用户已经确认的产品决定，以及 Apple Health／Fitness 导出数据手动导入需求。请把它作为本任务的完整执行指示，不要只执行其中的 Apple Health 部分。

## 0. 项目定位与目标

把现有 Health Trend PDF 从原型发展为准确、可追溯、易读的本机健康记录整理工具，重点是用药与化验／体检趋势、双语报告和可打印 PDF。不要声称“世界最佳”；应以公开、可复现的合成数据基准证明准确性、覆盖率、可追溯性和报告质量。

产品默认本机处理，不上传健康资料。它不是诊断、治疗、药物剂量建议或因果分析工具。

## 2. 用户已确认的产品决定（必须遵循）

1. 每次检查结果要保留该次原报告提供的参考范围及比较符号；不同医院、实验室、方法、年份或人群的范围不得混为一谈。
2. 重要指标在“必须关注的重要指标”区和其所属类别区**重复呈现是有意设计，必须保留**，以突出关键指标。
3. 最新体检报告中的其他文字也要纳入同一份 PDF，不应只有数值趋势图。包括检查所见、结论、医生／报告建议等；经用户核对后保留原文、报告日期和页码，不要让 OCR 未核对内容直接进入报告，也不要自动改写成模型的医疗建议。
4. 双语名称／用途、分类独立图、真实年份日期、趋势连线、最近三次数值标注、参考范围标示、红色异常提示、A4 横向 PDF 等既有约定继续有效。
5. 用户同意 Astra 的其他改进建议，但 Astra 只负责评审和建议；Grokbot 负责实现。未经用户明确要求，不要移除或改写以上既定报告样式。

## 3. Astra 评审：需要解决的问题

### P0：数据正确性、来源和个人身份

**3.1 每次观察值保存自己的报告参考范围**

当前设计／模型将范围放在指标层会导致新报告范围改变后，旧数据也被重新分类。请调整模型，使每个结果记录保留：原始数值、原始单位、低／高范围、比较符号（例如 `<`、`>`、`≤`、`≥`）、报告日期、实验室／机构、方法（可得时）、样本上下文（可得时）、来源文件及页码。范围缺失就留空，不得从别份报告或网络补值。

旧版记录的范围来源若无法确定，迁移时标记为“来源未验证”，不能假称是原报告区间。迁移应有版本号、迁移测试和失败回滚保护。

**3.2 不同参考范围在趋势图上的处理规则**

- 趋势线只表示实际测量值；每个点的异常状态都按该点自身报告的范围和比较符号判定。
- 不同来源／方法／日期的区间不得画成一组看似适用于全部历史数据的统一水平虚线。
- 默认可在每个测量日期附近显示该次报告区间标记，并清楚标注“该次报告参考范围”；只有来源和方法一致时才考虑连成区间带，来源或方法变化时断开。
- 如果提供“比较参考”视图，必须由用户主动选择，标明来源、适用人群／方法、单位和日期；它只供比较，不能改写原报告判定。网络范围只可作为待核对信息，不得自动套用。
- 不同单位默认分开绘图。换算只限经过验证的已知换算；必须保留原值、原单位、转换值、目标单位和依据。不能将 `<0.01` 或 `>90` 偷换成精确的 0.01 或 90。

**3.3 用真实时间比例画横轴**

当前按点的顺序等距放置会误导间隔。改为按真实日期间隔绘制；最近三次标完整日期；妥善处理同日多次检查、密集标签、长历史和局部放大。不得为了标签清楚而丢弃历史点。

**3.4 增加本机档案身份核对**

加入档案显示名／身份和导入前确认，PDF 显示档案所属人，降低本人、妈妈、父亲等资料混淆风险。OCR 检出的名字只能作为待确认线索；不匹配时提示，不得自动归档。不要把真实家庭成员资料放入测试。

### P1：用药与报告导入

**3.5 用药剂量历史和趋势图时间标记**

- 将用药方案做成有起止时间、剂量、频率、剂型的独立历史阶段，保留旧方案，不因编辑当前药物而抹除历史。
- 在关联指标图上以中性时间带／时间标记呈现剂量阶段；不声称药物导致指标变化，也不提供剂量调整建议。
- 日期未知必须明确未知；拒绝反向日期区间。
- 药物包装的 OCR 草稿须区分包装数量、单片规格、实际片数比例、服用频率和剂型，不能把“200 tablets”读成 200 mg 剂量。

**3.6 扩展报告识别并降低批量录入负担**

- 重点支持血细胞分析、生化报告中常见单位（包括 `10^9/L`、`10^12/L`）、小于／大于结果、定性结果、不同布局、多页和多语言别名。
- 使用报告级共享日期／机构信息、指标字典候选、别名映射、批量核对和同一报告重复导入检测；映射均需用户确认，不得自动确认。
- 对完全重复记录提示并避免重复写入；相似但值、来源或方法不同的记录列为冲突，由用户选择；提供撤销。
- 显示识别覆盖统计：识别候选数、用户确认数、未识别行数、跳过原因。不能把“识别完成”说成“整份报告已完整导入”。
- 提供原始页面／文字预览与来源页码，便于逐项核对；OCR 文本默认只在临时导入会话中，不保存原始文档。

**3.7 最新报告文字部分进入 PDF**

- 最新体检报告需有独立的“报告文字结论与建议”区，可按检查所见、结论、报告建议等原有标题分段。
- 由用户核对后保存被选中的文本，并记录报告名称、日期、机构、页码和段落来源；区分原文与用户备注。
- PDF 中以原文呈现，不由 AI 改写、归纳成诊断或生成建议。过长内容可分页／放入附录，不能截断而不提示。
- 同一份报告重复导入应检测重复；不同报告的文字不能拼接成一个无来源的段落。

### P2：图表、可追溯性、备份与发布

**3.8 报告可追溯**

- PDF 附录展示资料来源文件／页码、确认状态和修订说明；报告模板／版本有标识。
- 原始文件默认不留存；若以后提供本机保留原件选项，必须默认关闭、明确征得用户选择、提供删除能力，并说明备份敏感性。

**3.9 备份、恢复和离线宣称**

- 为 JSON 备份加入版本兼容、导入预览、冲突策略和失败可恢复设计；可评估可选加密导出。
- 如果 README 宣称离线可用，就实现并测试断网后重新打开和读取本机数据；仅仅浏览器缓存过模型不等于应用完全离线可用。

**3.10 PDF 规模测试与分类展示**

- 重点指标必须在重点区和类别区都出现（用户已确认此重复是设计要求）。
- 使用合成数据测试 23 项血细胞分析、67 项指标、多类别、长药物历史、长中英文名称、同日结果、不同区间、窄范围及密集日期。
- 逐页渲染并检查 PDF 的截字、重叠、遗漏、来源标注、图线和页码；不能只凭 build 或单元测试通过宣布完成。

## 4. Apple Health／Fitness 手动导入任务

本产品目前是静态网页。此任务只实现 iPhone「健康」导出 XML（如实际导出以 ZIP 封装，也支持安全读取 ZIP 内指定 XML）的**用户手动、本机导入**。不是 HealthKit 原生连接，不是实时或后台同步，不请求写入 Apple Health 的权限，也不增加云端服务。

### 目标流程

1. 用户从 iPhone「健康」导出全部健康和健身数据 XML，并在网页选择文件。
2. 浏览器本机解析；用户选择数据类别和日期范围。
3. 显示导入预览、来源、日期范围、将导入／重复／冲突／不支持数量。
4. 用户检查并确认后才写入本机；取消时不保存任何候选项。
5. 记录进入适当的健康活动类别和 PDF，不与化验指标混用不兼容单位。

Apple 官方支持页说明可从 iPhone「健康」导出全部健康和健身数据为 XML：<https://support.apple.com/zh-cn/guide/iphone/iph5ede58c3d/ios>

### 数据范围与语义

- 至少评估并支持常见数值 `Record`、`Workout` 训练记录、`ActivitySummary` 每日活动摘要；实际支持类型必须在 UI 和 README 列出。
- 可评估步数、活动能量、距离、运动时长、心率、体重、训练类型等；每种指标保留原始类型、数值、单位、开始／结束时间、来源 App／设备（存在时）、来源文件和导入时间。
- 区分单次样本、每日摘要和训练事件。不可在无明确选择时将样本求和、平均或把训练时段改成单点化验结果。任何聚合都须标明算法、时间周期和记录数。
- 不支持、未知、定性或格式异常数据要统计并解释，不猜值、不静默丢弃。
- ZIP 如支持，只读取被确认的 XML；忽略心电图、路线、附件等非目标数据。尤其不解析／存储 workout GPS 路线和位置轨迹。
- 日期解析保留原始偏移并正确处理本地日期，避免跨 UTC 时区导致日期跳变。
- 基于稳定指纹做幂等导入；同一记录不重复添加。相似但不能确定为重复的数据交由用户处理。

### 隐私与输入安全

- XML/ZIP 解压与解析全部在本机浏览器执行，禁止上传文件、XML 文本、健康字段或错误日志。
- 使用安全 XML 解析策略，拒绝 DTD、外部实体和外部资源；限制文件大小、解压后大小、节点深度和记录数，防止超大文件及 ZIP 炸弹。
- 原始文件／XML 默认仅临时保留在内存，确认完成或取消后释放；只保存用户核对确认的结构化数据。
- 只解析用户选择的类别和日期范围；不要默认导入用户不需要的敏感类型。
- 不加 HealthKit、OAuth、API key、后台服务、远程 AI、原生 iOS app 或实时同步功能；这些都超出本任务范围。

## 5. 建议实施顺序

1. 先给出代码现状差距、领域模型变化草图和分期计划，标明会触及的文件／schema 迁移／隐私文档。
2. 先做观察值范围与比较符号的 schema 设计、身份模型和迁移；确认不会重写历史语义。
3. 实现真实日期轴和每个结果的范围可视化；用真实间隔及不同实验室范围回归。
4. 实现可追踪的报告原文区与用药阶段记录／时间标记。
5. 实现安全、可复核、去重的 Apple Health XML／ZIP 本机导入和类别筛选。
6. 补齐批量识别、报告覆盖率、报告来源附录、备份恢复和用户文档。
7. 任何阶段如需超出本文件范围，先列出差异并征求用户决定，不自行扩张。

## 6. 验收标准

- 两个合成报告为同一指标提供不同单位／范围／实验室时，历史范围、原始值和异常判定不被后来报告改写；缺失范围维持未知。
- `<`、`>`、`≤`、`≥` 与定性结果保持原始语义，不当作精确数值。
- 2024–2026 不规则日期按真实时间间距呈现，最近三次日期完整；同日多次数据可辨认。
- 重点指标仍在重点区与所属类别区重复显示。
- 报告文字可以确认、取消、修订并追溯来源；未核对 OCR 不会出现在 PDF。
- 合成 23 项 CBC 和 67 项指标可逐项核对识别、漏项和来源；导入重复不会静默新增。
- Apple Health 样本／活动摘要／workout 类型、单位、时间偏移和来源都能在预览中核对；取消完全不落盘，重复导入幂等。
- 恶意 XML/ZIP、外部实体、过大文件和解压炸弹测试被安全拒绝。
- Playwright／网络测试证明没有健康数据或导入文件传出浏览器。
- 全尺寸合成 PDF 每页经渲染检查无截断、重叠、缺线、范围错配或来源缺失。
- 迁移、备份恢复失败不会破坏原本地记录；旧版本数据有测试覆盖。
- 发布说明区分已完成、部分完成、暂缓及不支持项目；不得宣传无基准支持的通用 OCR 准确率或未实现的 HealthKit 实时连接。

## 7. 明确暂缓事项

本阶段不实现云端 AI、账号体系、远程分享、设备同步、药物相互作用／剂量建议、诊断／治疗建议、自动采用网络参考值、健康数据上传、HealthKit 原生实时连接或 FHIR/IPS 合规导出。LOINC／FHIR 可在核心数据模型稳定后另行评审，未经标准验证不得宣称合规。
